## What G3 is

The module `chartulary::quads`: a dictionary and quad index over dense term ids, generic over the term type, with no new dependency (brief D1, plan D2). Brief §1 measured Mere's SPARQL adapter re-scanning the whole graph for every pattern. This is the store half of the fix. Mere's engine supplies the terms and implements its evaluator's dataset seam over this index (plan P2). Eidetic indexes the ids it is handed and never learns Mere's literal or reifier vocabulary.

- **`Dictionary<T: Hash + Eq + Clone>`.** Append-only: `intern`, `lookup`, `resolve`, `get`, `len`. A rebuild makes a new dictionary (brief D2, D4).
- **`TermId`.** A `NonZeroU32` minted from 1, so `Option<TermId>` is four bytes. `TermId::DEFAULT_GRAPH` is `u32::MAX`, and no dictionary mints or resolves it (plan D5). A caller never interns a term for the default graph: it passes the reserved id.
- **`Quad` and `QuadMeta`.** A quad is four ids. Its meta records whether it is held, plus an optional asserter and statement: the fields a filter needs beside the triple (brief §3).
- **`QuadIndex::build`.** Collapses identical `(quad, meta)` rows but keeps every distinct meta of a quad (plan D6). It stores one base table sorted SPO then graph, and five orderings of `u32` positions into it: POS, OSP and the graph-first GSPO, GPOS, GOSP (brief D3, plan D4).
- **`pattern(s, p, o, g, view)`.** Picks the ordering whose prefix the bound positions fill, finds one range of it by binary search, and walks it. Each quad comes out once per view, its held row first. `View::Live` skips withdrawn rows and `View::History` keeps them (brief D5). For the graph, `Some(None)` is the default graph.
- **`graph_names(view)` and `contains_graph(id, view)`.** These list only the named graphs that have a row visible in the view, so Mere's withdrawn-only history graph is absent from a live read (plan D7). The default graph is never listed.
- **`QuadIndex::apply(asserted, withdrawn)`.** Maintains the index in place between rebuilds (plan P4, D9). Asserted rows already present are ignored; new ones are appended to the base table and entered in each ordering at their sorted place, one backward pass per ordering for the whole batch. A withdrawal names a row by quad, asserter and statement and flips its held flag; no ordering moves. If the withdrawn row already exists, the held one is dropped as a duplicate (a bitset, skipped by every read). With no held row, the withdrawn row is added. Asserts go first, then withdrawals. `build` stays the fallback and the test oracle.
- **`len()` and `memory_bytes()`.** `len()` counts stored rows; `memory_bytes()` is there for the measurement. Each row costs 28 bytes in the base table plus 20 across the five orderings, so 80,000 quads take 3,840,200 bytes, against brief §4's 10 MB cap. The first `apply` adds a sixth ordering (SPOG, 4 bytes a row, which the sorted base table served until then), and growth is by a sixteenth rather than doubling: at 800,000 rows the index goes from 38.4 MB built to 44.2 MB after edits.

## Tests

The tests live in `crates/chartulary/src/quads/tests.rs`. A generated dataset of 3,000 rows has exact duplicates, quads repeated with differing metas, four named graphs (one holding only withdrawn rows) and the default graph. On it, every one of the sixteen bound shapes is checked in both views against a brute-force filter. Further tests cover the default graph as `Some(None)`, collapsing and held-first yield, `graph_names` and `contains_graph` under each view, the dictionary's reserved id, and an index of `chartulary::rdf::to_quads` interned as `rdf::Term`, which gained `Hash` for it. One test pins the 80k memory figure under 10 MB. `apply_tests.rs` checks `apply` against `build` over the same final rows: random batches of asserts and withdrawals over a small id space (60 seeds, 25 batches each, from an empty index and from a built one), and the 3,000-row dataset edited in place. Each check compares every bound shape in both views, in yield order, plus `graph_names`, `contains_graph` and `len`. Breaking the flip or the held-first choice fails both tests. `examples/quads_apply.rs` times `apply` at 800,000 rows (release): one 8-row statement asserted costs 0.54 to 0.80 ms (median of 101, over three runs on a machine shared with other builds), a withdrawal of those rows 0.003 ms, and the first apply after a build 7 to 20 ms.

## Not here

The `spareval` seam, the `oxrdf` term type and the conformance layer are Mere's (plan P2). So is the id for a term the dictionary lacks: `TermId::from_u32` lets P2 name one that matches no row. Deriving reifier rows on read waits on a memory number (plan D1). So does compaction of dropped rows, which a rebuild does.

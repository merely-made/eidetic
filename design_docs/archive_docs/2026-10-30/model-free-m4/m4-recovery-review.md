# M4 bounded recovery and cooperative lease review

Reviewed the task package against the storage extension design and recovery report. All 25 source hashes in `m4-recovery-review-sources.json` matched at review time. The review covers the submitted Fjall recovery and lease changes; it does not qualify the in-flight LSM bounded-read and `PreparedTree` implementation or the receiving Muniment/host layers. No test suites were rerun. The cited 34-case combined matrix is interim evidence for the recorded source closure, not a final gate.

**Spec verdict: not yet met. Quality verdict: Needs fixes.** The temporary-keyspace lease has a concrete hole. The requested-capacity ledger also lacks a demonstrable charge for an allocation induced by each recovered partition. The LSM commit boundary remains unverified and can affect the central no-limit-after-mutation guarantee.

## Findings

### Important: temporary cleanup removes the lock while capabilities retain it

`support/patches/fjall/src/keyspace.rs:123` removes the entire directory when the last `Keyspace` is dropped with `temporary(true)`. `support/patches/fjall/src/partition/mod.rs:392` and `support/patches/fjall/src/snapshot_tracker.rs:15` keep an `Arc<File>` lease alive for escaping iterators and snapshot nonces, but on Linux removal unlinks `.fjall-owner.lock` even while that file is open and locked. An updated second owner can then call `lock_owner` (`keyspace.rs:390`), recreate the directory and a new lock inode, and successfully open the same path while a partition, snapshot, or iterator from the old owner survives. The old capability also points at a removed store. This breaks the advertised lease across updated opens and escaping capabilities; retaining a file descriptor alone does not retain a namespace lock after its file is unlinked.

Defer temporary directory removal until the last capability holding the owner lease is gone, or otherwise ensure the coordination inode cannot be replaced while any capability exists. Add a focused Linux regression for ordinary and bounded temporary opens: retain a partition, snapshot, iterator, and transactional iterator across `Keyspace` drop, then ensure another updated owner cannot acquire that path until each last capability drops. Check target-specific deletion semantics separately.

### Important: failed temporary recovery can delete the store

`support/patches/fjall/src/bounded_recovery/store/commit.rs:141` disables `clean_path_on_drop` during preparation to protect a refused open, but restores it at line 322 before `PreparedTree::commit`, cleanup, journal truncation, sync, and background startup. An I/O error in any of those subsequent operations drops the not-returned `Keyspace`, and its destructor recursively deletes the entire existing store (`keyspace.rs:123`). Even though I/O failure after admitted actions may leave partial repairs, deleting every retained file when opening fails is a much larger and avoidable consequence. Keep automatic temporary cleanup disarmed until open has succeeded and ownership is handed to the caller. A focused fault-injection regression should force a post-admission I/O failure for a pre-existing temporary-marked store and check that unrelated retained files remain.

### Important: per-partition config path clones lack an identifiable admission charge

`support/patches/fjall/src/bounded_recovery/store/commit.rs:165` charges the handle vector and `PartitionHandleInner` allocations, and lines 169-180 charge the partition key. Each recovered partition then calls `PartitionHandle::from_keyspace` at line 200, which clones `keyspace.config` (`support/patches/fjall/src/partition/mod.rs:262`); that clone allocates a fresh `PathBuf` containing the configured root. The number of these allocations is determined by the stored partition count. There is no explicit per-handle path-capacity charge in this loop. The earlier `path_bytes * 8 + 256` charge at `store.rs:331` precedes LSM tree-config setup, but does not identify or prove coverage for the later Fjall config clone as well as the tree's own path requests. The directory's conservative name precharges cannot establish a requested-capacity guarantee for an unrelated later allocation without a documented combined bound.

Charge the per-partition config path copy before constructing each handle, or document and verify a single conservative combined bound that explicitly covers both the LSM preparation requests and all Fjall config clones. Verify a many-partition, long-root fixture with an allocation ledger instrumented at these requests and an exact exhaustion boundary, including a recursive before/after inventory on refusal. Fixed cache, descriptor infrastructure, allocator overhead and RSS are outside this finding.

## Strengths and evidence

- One budget identity is retained from journal admission through replay; journal values, combined partition/key lengths, physical input, replay work and requested payload capacities are checked before their respective copies. Metadata also consumes allocation capacity. Replay scans count repeated work and use checked size arithmetic. The pinned skiplist's node layout has a maximum 32-pointer tower; the source-derived per-entry bound is conservative for that node itself.
- Journal decoding streams the original item encoding into the checksum. Invalid tags, batch count mismatch, trailers, UTF-8 and checksum failures are explicit corruption; a limit propagates directly rather than being sent through upstream truncating readers. Zero padding is scanned completely before a repair is planned. EOF ambiguity and power-loss salvage remain bounded by the report's stated limitations.
- Existing-store recovery prepares journals, partition options, trees, replay, queues, watermarks, and filesystem actions while retaining the owner lock. Cleanup and journal repairs are deferred until after Fjall's pre-action budget checks. Blob trees and the optional bytes-backed replay representation refuse explicitly. The tests include inventories of pre-existing lock and data files, including earlier repair/cleanup candidates followed by later refusal.
- The sealed write-buffer accounting and per-task startup wakeups have focused green receipts after preserved failures. The partial-flush/reopen/subsequent-flush case is useful evidence, but is not a general power-loss or FIFO qualification.

## Cannot verify in this review

- `PreparedTree::prepare`, `install_replay`, `tree()`, and especially `PreparedTree::commit` at `commit.rs:327` are a separate in-flight LSM change. The controller must verify that all stored-input-driven reads, metadata allocations, capacity checks, cleanup paths, and known native path conversions are admitted against this same ledger before the first mutation; that `commit` cannot return a configured limit or do a new limit-bearing read after any prior tree has committed; and that the tree, segment descriptors, iterators and snapshots remain valid across owner and prepared-tree lifetimes. The reported descriptor-retention repair needs its own regression and re-review. Without this boundary, a Fjall-only inspection cannot prove whole-store preservation or complete standard-tree metadata.
- Inspect actual end-to-end error translation, bounded ordinary and structured reads, per-entry write admission, owner settings, and host open/reopen call sites in the separate Muniment and host reviews. This package does not establish them.
- Linux receipts do not demonstrate macOS or Windows runtime locking, path conversion, or deletion behavior. The source-derived directory/path allocation estimates and the stated Windows unsupported long/nonabsolute path must be independently checked for the actual supported Rust/toolchain and platform. Other targets explicitly refuse bounded admission.
- The implementation report states a final frozen source closure and connected supplier, Muniment, and workspace gates remain pending. The inventory matched this submitted recovery package, not concurrent in-flight LSM work. Existing v2 journal/config compatibility and the partial-flush behavior have focused evidence, not complete compatibility qualification. The reported v3 FIFO fix is not evidence to backport its particular change to v2.

## Scoped re-review, fix round 1

The following verdicts supersede the three findings above for the reviewed fix snapshot. I read `m4-recovery-review-fix1.diff`, the updated recovery report, and the LSM commit clarification. All 11 fix-package source hashes and all 207 paths in `m4-storage-review1-sources.json` matched at review time; the inventory file itself has SHA-256 `ea0a7a2623356c7d042ca1a0db8c83c390a1d1e0f448559e4a18f76f9d87da4b`. No tests were rerun.

1. **Temporary cleanup removes the lock while capabilities retain it: ADDRESSED.** `OwnerLease` owns the locked file and runs cleanup only in its final drop, while that file remains locked. Its cleanup keeps the root and `.fjall-owner.lock` inode, as the controller specified. Partition handles, snapshot trackers and leased iterators retain the shared lease. The supplied Linux lifecycle and synchronized reopen receipts cover the intended behavior. The empty coordination directory is a deliberate change to temporary semantics; platform-specific behavior beyond the Linux receipt remains unqualified.
2. **Failed temporary recovery can delete the store: ADDRESSED.** The lease starts disarmed, and bounded open arms cleanup only after retained filesystem actions, journal sync and background startup succeed (`bounded_recovery/store/commit.rs:377` and `store.rs:247`). The supplied focused permission-error regression covers a post-admission failure. An I/O failure may still leave already-admitted partial repairs; the fix prevents automatic whole-store cleanup of the failed open.
3. **Per-partition config path clones lack an identifiable admission charge: ADDRESSED.** `charge_handle_path` debits metadata and allocation before each `PartitionHandle::from_keyspace` config clone (`commit.rs:43`, `commit.rs:220`); it is separate from the earlier tree-config charge. The supplied many-partition long-path test instruments the eighth charge, checks a one-byte-short refusal and pre-existing inventory, and checks the exact charge boundary.

**No new Important or Critical findings in the scoped fix diff.** The final recovery-fix verdict is **Approved for these three findings**, subject to the distinct LSM findings, supplier/consumer closure, and other limitations already recorded. This does not approve the entire M4 extension.

Cross-tree sequencing is now source-established on the Fjall side: `store.rs` prepares all partitions and calls `install_replay` for each before constructing the `RecoveryPlan`; only after that does `commit.rs` begin its loop consuming `PreparedTree::commit`. Thus Fjall does not commit one prepared tree and then install replay in another. The separate LSM clarification states that a prepared-tree commit performs no content reads or configured checks and precharges known path conversions. This combined ordering is conditional on that LSM review and its unresolved malformed index extent/pointer finding, platform path estimates, and final source closure; it does not by itself establish whole-store admission for malformed metadata.

Reported current-source receipts are `m4-store-review-wave-lsm-1` (64), `m4-store-review-wave-muniment-1` (117), and `m4-recovery-review-fjall-unit-2` (2), all locked/offline as recorded by the implementation report. They are evidence for their specific frozen closure, not fresh runs by this reviewer or a whole-product qualification.

# M5 cold-copy B: retained clip open contention

## Observed and limits

B's `sandbox/reopen/scenario.done` reports the selection content failure, then a 600-frame search wait failure and presentation watchdog failure. `app.log:93` records the former at 19:37:56.075Z for node `5ef46c38-f4e6-4170-8676-89a17f2577d8`. This is a failed diagnostic, not a qualification. Neither log records the owner of the lock or the precise timing of another open; search wait and watchdog are separate symptoms, not proven consequences of this error. No live reproduction or instrumented run was performed.

The diagnostic profile contains `sandbox/profile/retained-clips/.fjall-owner.lock` (inode 27164364, link count 1 at inspection). The attempted path is the active clip destination root joined with `retained-clips`, and then `.fjall-owner.lock`. The profile is the likely root in B; the error does not itself log the resolved root or inode, so exact identity at failure remains unobserved. `namespace_phase.py:211` sets the isolated XDG data home; the retained profile is in the diagnostic sandbox. The copied lock file's existence is not a held lock: Fjall uses an OS lock on an open file, and a new copy does not transfer that lock. This does not rule out another live process or inherited/shared inode at the time. A restored multi-tile layout alone establishes neither contention nor its owner.

## Source trace

* `src/shell/effects/shell_effect_spawn_content.rs:68-94` resolves the retained clip on content spawn. The research-citation route calls `research_clip_document` (`src/app/research_clip_arms.rs:80-123`); its fallback calls `read_sealed_with_limits` directly. Both ultimately use `read_sealed_bounded` (`src/retained_clip.rs:309-327`). The error formatting exactly matches its `SourceReadError::open("Retained clip", ...)`.
* Every such call opens a new `FjallStore` at `root/retained-clips` with configured owner limits, creates a per-operation `BudgetStore`, reads the sealed view, and drops the local owner when the call returns. The citation `ClipReader` cache holds target, generation, identity and custody epoch, not a store handle (`research_clip_arms.rs:57-66`; `research.rs:76`). Fleece's document decoding runs on the provided store; it does not supply a persistent common owner.
* `research_search.rs:417-470` runs jobs on a dedicated thread, distinct from shell spawn. Its snapshot iterates admitted clips and calls `Bridge::clip_view_bounded` (`research_search.rs:299-303`), which performs the same independent store open (`research.rs:293-311`). Compare and structured-record jobs also route through that worker and bounded clip read. Admission, import and control paths have independent opens too (`retained_clip.rs:139, 261, 321`; shell effect open-theme-workshop). The shared operation budget is a ledger, not a lock or shared database owner.
* Muniment forwards bounded recovery errors as `fjall open: ...` (`crates/muniment/src/fjall_bounded.rs:48-65,188-205`). Patched Fjall acquires a nonblocking exclusive file lock during bounded recovery (`support/patches/fjall/src/bounded_recovery/store.rs:204`; `keyspace.rs:430-455`). The owner lease is retained by keyspace/partition and snapshot/iterator capabilities until their last drop (`keyspace.rs:39-46`, `snapshot_tracker.rs:13`, `iter.rs:8`); the M4 tests explicitly exercise extended lifetimes (`crates/muniment/src/fjall_backend.rs:226-290`). Thus a second independently opened owner can fail even inside one process. Ordinary persisted `.fjall-owner.lock` is intentional and is not itself a stale lock.

## Assessment and next step

There is a concrete product concurrency hazard: the worker and UI may independently open the same exclusive store at overlapping times. B's exact competing owner remains unknown; the source and failure alone do not prove worker-versus-UI overlap, or exclude a diagnostic-specific process. To establish B's cause, capture resolved canonical path and lock inode, process/thread and operation, and acquire/drop times around every retained-clip owner, plus kernel lock owner while live. Preserve the original failure and repeat on an independent copy only after instrumenting. Check whether the previous reader's owner lease has actually ended, including any retained capability, before attributing it to a concurrent call.

Smallest sound product direction, once overlap is confirmed: coordinate all in-process reads and writes through one owner per actual retained-clips store, or serialize the entire open/use/drop lifecycle through one owner boundary. Include presentation, search, comparison, structured queries, retention, import and control; preserve configured owner limits, separate shared per-operation read ledgers, custody epoch rechecks and teardown/session lifecycle. Avoid waiting on the UI thread indefinitely; external process contention must still fail explicitly. A deterministic test should hold one operation at a barrier while another starts, verify both admitted operations complete under the chosen coordination, verify cross-process busy remains visible, and exercise close/reopen plus limit and custody changes. No retry loop or widened bounds is warranted by the evidence.

The initial pin-only change during review was superseded by the final frozen hashes above. No tests or builds were run by this reviewer. The implementer reports 26 focused tests passing. No complete native receipt exists, and the unconditional draft guard remains.

1. **P1: The Sum semantic check can accept omitted eligible inputs.** `verify.py:387-398` filters the independently inspected snapshot before calling `verify_operation_semantics`; that function at `m5-draft/verify_receipt.py:187-191` checks only that one row says 19 and names two integer contributors valued 7 and 12. It does not require these IDs to equal the entire filtered record set, or independently establish one property/schema, compatible units/types, checked arithmetic and correct source contributors. For example, if a third eligible `m5:amount` record exists but the product silently omits it, a row naming only 7 and 12 passes. The owner inventory being complete does not close this gap because it is not compared to the Sum row's contributor set. **Fix:** derive the complete eligible ID set from the owner-backed filtered snapshot, require exact unique contributors and source references, verify compatible schema/type/unit and checked arithmetic, and compare the independently computed value. Add a regression with an extra eligible record and other wrong-unit, overflow and wrong-contributor cases.

2. **P1: Negative query checks do not establish the query or the cause of refusal.** `verify.py:455-465` delegates no-match and over-limit to `m5-draft/verify_receipt.py:230-235`. No-match passes for any complete snapshot with no rows, including a foreign/empty scope or an operation unrelated to the intended unmatched property; it is not checked against the independently inspected post-withdrawal inventory or the `m5:absent` filter. Over-limit accepts any nonempty error, such as custody or source failure, without binding the lowered Records limit, attempted query, scope, or actual limit refusal. The frame mapping cannot supply these machine-checked conditions by itself. **Fix:** bind the negative observations to the same session, graph, intended source scope and independently verified post-withdrawal inputs; assert the exact operation/filter and derive the empty eligible set for no-match. For over-limit capture the effective setting, relevant query/input count and explicit limit-specific refusal, and require those facts rather than any error. Test foreign scope, wrong query, unrelated error and unchanged limit.

3. **P1: The required explicit source comparison and headed evidence are not verified.** The seed scenario records `exact_pair.comparison.json` and `exact_pair.png` (`m5-draft/seed-composed.draft.scn:198-209`), but `verify.py:381-485` never reads that observation or compares its left/right IDs, immutable versions, hashes, relationship and spans with the independently opened A1/A2 sources. Nor does the required frame set at `:475-479` include that comparison, selected-source/citation frames, exact A1 reopen, selection/note reopen, authoring frames, or the fresh empty-scope result. A review listing only the current set can therefore satisfy its checks while these required product-use claims have no reviewed frame. The cited-note file being present in a ledger alone does not check its citation identity or rendered content. **Fix:** bind and validate the recorded comparison against both exact inspected sources, verify the saved citation and selected-source identity/quote/selector through the relevant seed and reopen observations, and require human outcome mappings for the actual comparison, citation, source/selection/note reopen, authoring, and both sides of the scope-switch evidence. Add missing/mismatched comparison and missing-frame tests.

4. **P1: Intact collector script and scenario hashes are not joined to the frozen input manifest.** The approved collector records hashes of its frozen scripts and scenarios in `inputs.json.files` (`m5-missing-draft/run_acceptance.py:157-163,190-192`). The assembler's `check_builds` checks only the three binaries and build receipts (`assemble.py:40-68`); it does not compare those script/scenario hashes to the corresponding `frozen/` ledger bytes. `verify.py:315-319` performs this binding for the fault inputs only. Thus a ledger-bound intact script or scenario can differ from what the recorded input hash says was launched, while the receipt integration accepts both independently. Further, standalone `verify_draft` never repeats the assembler's build receipt/source/provenance linkage checks, so it relies on having run a particular assembler instead of validating those relationships from the receipt. **Fix:** require every intact frozen script and scenario listed in `inputs.json.files` to be present and match both the source ledger and receipt copy, and revalidate all available build/provenance/source inventory/command links in the standalone verifier. Keep the binary hash established at assembly explicit because binaries are intentionally not copied. Add mismatched frozen-script and altered build-link cases.

5. **P2: Other row fields are not fully checked against the independently derived result.** `verify.py:92-108` derives equality groups from records and validates the row value and contributor set, but does not check `row.group`, which carries the actual entity/property/schema/context/status/time/value group key. The Count-by-source check at `m5-draft/verify_receipt.py:126-136` permits two rows for the same source if their distinct record IDs partition its contributors, and does not validate the row's `sources` field. Comparison class validation also lacks a final rejection for an unrecognized class (`:167-186`). These can make incorrect result identity or duplicate source groups look valid. **Fix:** verify complete group-key fields, one count row per source and exact source references, and reject any comparison class outside the supported set; add focused mutation tests.

The assembler creates a separate new receipt directory and checks the original ledgers and profile inventory before copying. The standalone verifier invokes the pinned full `verify_bound_case`, and it preserves unknown resident-model loads rather than treating them as zero. Those checks do not replace the missing semantic and provenance bindings above. The reviewed fault-driver repin is a known integration dependency, not a new finding here. Real intact/fault runs, copy-integrity evidence and human frame review remain pending; the draft guard must remain in place.
